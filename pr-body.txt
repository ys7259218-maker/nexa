## Inbox customer-number search reaches beyond the newest 200

The last slice (#154) capped the conversations inbox list at 200 rows so the
page stays bounded past Supabase's 1,000-row default — but that meant searching
only filtered the 200 rows already loaded, so an old conversation could not be
found by phone number. This slice closes that gap by running the search in the
database.

### Changes
- `getConversationInbox(client, requestedId, customerSearch)` — when a customer
  query is present, the conversations list is fetched with
  `.ilike("customer_wa_id", "%<digits>%")` (bounded to `CONVERSATIONS_LIST_LIMIT`)
  instead of just the newest rows. The deep-link by-id fallback and the thread
  cap behave exactly as before.
- The query value is the `parseCustomerSearchValue` output the page already
  produces — digits only, so LIKE wildcards cannot be injected.
- `app/conversations/page.tsx` passes `customerQuery` through to the helper; the
  existing client-side digit filter and triage chips still apply on top.
- `FakeQuery` gained `ilike`; tests cover the DB-search path, the no-search
  newest-first path, and the contract pins (`.ilike(...)` call + 3-arg page call).

Verified: lint 0 errors, typecheck clean, `npm test` 407 passing, production
build compiles, Playwright smoke 5/5, `npm audit` 0 vulnerabilities.

No migrations, no production changes — query/page/test-only.
