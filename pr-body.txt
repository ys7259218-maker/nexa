Operators can now inspect the durable inbound webhook ledger instead of digging in the database blind. This preserves the table's security posture: `webhook_events` has no RLS policies (opaque to normal clients), so reads go through a server-only service-role API route.

## What changes
- `lib/webhookLedger.ts`:
  - `WebhookEventStatusFilter = "all" | "claimed" | "processed" | "skipped" | "failed"`.
  - `parseWebhookStatusFilter(value)` — validates unknown search-param input, defaulting to `all`.
  - `webhookStatusLabel(status)` — display labels for each status.
  - `listWebhookEvents(createClient, filter, limit)` — reads `webhook_events`, newest first, with optional status filter; returns a typed result or an error string.
- `app/api/ops/webhook-events/route.ts` — auth-gated, server-only API route that fans out to the service-role client.
- `app/settings/webhook-ledger/page.tsx` — status filter chips, event rows (kind, type, status chip, event id, masked sender, last error, timestamp), empty and error states.
- `components/dashboard/Sidebar.tsx` — "Webhook ledger" link beside the readiness pages.

## Privacy
- Sender IDs are masked with `maskWhatsAppId`; the event id is the internal ledger key (uuid), not customer PII. The page notes raw bodies are stored only for replay.
